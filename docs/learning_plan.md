# 学習プラン（ROS2 × Python/C++ でシミュレーション環境を作る）

[`docs/idea_origin.md`](idea_origin.md) のロードマップ（ステップ0〜7）を、学習の5テーマ×2言語の視点で実行順に並べ直したもの。技術選定の決定事項（Jazzy、PI制御、1D質点、オイラー法、rqt_plot 等）は [`docs/idea_origin.md`](idea_origin.md) を正とし、ここでは繰り返さない。

## 目的とゴール

- 目的: ROS2の実務スキルを一通り身に着けながら、「慣性のある車両を目標速度に追従させるシミュレーション」を完成させる。
- 5テーマ: (A) `ros2` コマンド / (B) パッケージ作成 / (C) launchファイル / (D) ノードのプログラミング / (E) 有名OSSの活用。
- 各テーマを **Python（rclpy）とC++（rclcpp）の両方**で試す。ただし言語差が本質でない項目は片方で足りる（下表の「言語」列）。ノードのプログラミング（D）は、フェーズ3-1（トピック）だけ両言語を必須とし、3-2〜3-5のC++版は任意とする（2026-09-24、ユーザー判断。フェーズ5がPython中心のため）。

## フェーズ計画

各フェーズの完了条件を満たしてから次へ進む。所要は目安（1コマ＝1〜2時間の学習セッション）。

### 環境構築（ステップ0）— 2時間程度

- 内容: WSL2・Ubuntu 24.04・ROS2 Jazzyの導入（[`docs/setup_wsl2_ros2.md`](setup_wsl2_ros2.md)）。別ドライブへの移動（2b節）と、GitHubの認証・Claude Codeの環境（7節）は任意。
- 完了条件: `ros2 run demo_nodes_cpp talker` と `ros2 run demo_nodes_py listener` の間でメッセージが届く。フェーズ0（読み物）とは、どちらを先にしてもよい。

### フェーズ0: ROS2の概要（読み物）— 1コマ

- 内容: ROS2の通信の仕組みの概要（層を積み重ねた構造。DDS・RMW等の詳細は[`docs/tips.md`](tips.md)の6節）、ROS2で実現できること、業界ごとの活用（製造業・モビリティ・建設業・ドローン・介護）、基本用語、学習しなければならない概念の地図、よく使われる周辺開発ツールを整理した読み物。コマンド実行はしない。
- 完了条件: ROS2の通信が層を積み重ねた構造（プロトコルスタック）になっていることと、本文の用語（ノード・トピック・サービス・アクション・パラメータ等）を自分の言葉で説明できる。

### フェーズ5: 車両シミュレーション本体（D・C）— 7〜11コマ（5-0の1〜2コマ、5-4の2〜3コマを含む）

- 5-0（ステップ5を前倒し）Gazeboの導入: Gazebo Harmonic（`ros-jazzy-ros-gz`）を導入し、公式のデモ集 `ros_gz_sim_demos` の2輪車（diff_driveのデモ）を、`ros2 topic pub` と自作のPublisherで走らせる。前提はフェーズ1と3-1だけ（2026-09-24、ユーザー判断。位置づけは暫定で、作りながらフェーズ8（当時のフェーズ7）や任意の発展へ移す可能性がある）。1〜3節（導入とCLIでの操作）は、動くものを楽しむ寄り道として、フェーズ1の後に試してもよい（2026-09-28、ユーザー判断。完全な理解は求めない）。
- 5-1〜5-4の進め方（2026-09-26、ユーザー判断）: 学習の中心は、疑似プラントとPI制御の数理モデルを自作すること。Gazeboのワールドや車両（URDF・SDF）は自作せず、5-0の `ros_gz_sim_demos` の `diff_drive.launch.py` を取り込んで使う。5-4では、このデモのワールドファイル（`diff_drive.sdf`）を写して一部だけ改造する（この補足は2026-09-26、Claude独自判断）。Gazeboは次の2段階で使う。
  - 5-1〜5-3: Gazeboは**表示器**。制御のループは自作のノードだけで閉じ、プラントが計算した速度に縮尺をかけて、緑の車両の `cmd_vel` へ送る表示用ノードで動きを見せる。プラントは実車の単位（質量1500 kg・最高20 m/s程度）で作り、縮尺は1/40を目安にする（デモの車両は最高0.5 m/s・加速度の上限1 m/s²のため。縮尺は表示の直前にかけるだけで、プラントの計算には影響しない）。
  - 5-4: プラントを**Gazeboの物理に差し替える**。PI制御ノードは変えずにつなぎ替え、プラントを差し替えても制御ノードをそのまま使えるというROS2の利点を体験する。
- 5-1（ステップ2）疑似プラントノード: 1D質点＋アクセル/ブレーキ別の一次遅れ＋オイラー積分。抵抗は、空気抵抗を線形にした速度に比例する抵抗と、一定の転がり抵抗（手計算で定常速度と時定数を求められるよう線形にする。2026-09-26、ユーザー判断）。時定数などの車両の値はパラメータにし、既定値は妥当な範囲でClaudeが選ぶ（同日、ユーザー判断）。入力はペダルの指令（`/plant/pedal`、−1〜1）、出力は現在速度（`/plant/velocity`）で、どちらも `std_msgs/msg/Float64`。モデル部はROS2に依存しないPythonのクラスとして書き、ノードはそれを包むだけにする（トピックI/Fからの分離）。表示用ノードもここで作り、アクセル一定で加速して一定の速さに落ち着く様子をGazeboで見せる。
- 5-2（ステップ3）PI制御ノード: Kp/Kiをparameter化し、YAMLで与えて `ros2 param set` で調整。ループが閉じて目標速度に追従し、ゲインを変えるとGazeboの車の動きが変わる。目標速度はトピック（`/target_velocity`）で受け取る。PI制御の式もROS2に依存しないクラスに分け、5-1のモデルとつないだ閉ループのシミュレーションで、P制御だけの偏差・ワインドアップ・時定数を変えたときの違いを確かめる（2026-09-26、Claude独自判断）。
- 5-3 launch化: 目標速度発生・PI制御・プラント・表示用の各ノードと、`diff_drive.launch.py` を1つのlaunchで起動。目標速度を階段状に変えて追従を見る。目標速度発生ノード `target_generator` は、起動からの経過時間で階段状に目標を変える（時刻と値は配列のパラメータ）。5-0のデモは `IncludeLaunchDescription` で取り込み、引数 `gazebo` で外せるようにし、パラメータは1つのYAMLにまとめる。`rqt_plot` で目標・速度・ペダルを重ね、非対称性をグラフで読む（詳しい使い方はフェーズ6）。目標0で積分の項が残って止まりきらない現象と、その対策を課題として扱う（2026-09-26、Claude独自判断）。
- 5-4 Gazeboの物理で閉ループ: `diff_drive.sdf` を元に、緑の車両のDiffDriveを外して車輪にトルクをかける仕組み（ApplyJointForce）と速度を出す仕組み（OdometryPublisher）を足したワールドを用意する（DiffDriveは車輪の速度を毎ステップ指定するため、外から力を加えても打ち消されるので、改造が要る）。元のファイルはApache-2.0で、読者が各自で写して改造する形にし、リポジトリにはファイルそのものを含めない（出典と変更点のコメントと、差し替えるプラグインの記述だけを手順書に載せる。そのため `LICENSE` の第三者の一覧は変えない。2026-09-26、Claude独自判断）。自作するのはアクセル/ブレーキの遅れ（アクチュエータ）の部分で、車両の質量・摩擦はGazeboが計算する。RTFが100%を下回るため、`/clock` を中継して `use_sim_time` を使う。縮尺は速度1/40、力は有効質量（車輪・補助輪の回転の慣性を含めて約11.4 kg。実験で確認）から約1.9×10⁻⁴。ブレーキは速度の向きと逆にかけ、止まる直前で弱める。`target_generator` は現実の時間のまま（2026-09-26、Claude独自判断）。
- 完了条件: ステップ入力の目標速度に対して追従し、アクセル/ブレーキの非対称性の影響をグラフで説明できる。5-4では、同じゲインで自作のプラントとGazeboの物理の追従の違いを説明できる。
- 言語方針（決定）: **Pythonをベースに実装する**。C++版は参考程度に、余力があれば作る（作る場合はトピックI/Fを同じにして、Python版と差し替え可能にする）。

### フェーズ6: 可視化・記録（E）— 3〜5コマ（見込み）

- 着地（2026-09-26、ユーザー判断）: 「グラフで見た違いを、数で言えるようにする」まで進める。`rqt_plot` で見る → `ros2 bag` で記録する → 再生して同じグラフを見直す → 解析のノードで記録から指標を計算し、条件ごとの比較表を作る。指標は、ステップ6（強化学習）の報酬を作る下地にもなる。
- 題材（2026-09-26、ユーザー判断）: 5-3と5-4の両方で試す。5-3で学び、5-4はサンプルを動かす程度（記録の再生でのシミュレーション時刻の扱いだけを補足する）。
- 分量（2026-09-26、ユーザー判断）: 学習者が可視化の題材で動機を保てるよう、3冊にまとめる。書いてみて膨らんだら分割する。各冊は、フェーズ5で残った問い（例: 5-3と5-4の違いは重ねるとどう見えるか、5-4の行き過ぎは何%か）から始め、数を出す前にグラフから予想させる。
- 冊の分け方:
  - 6-1 記録して見直す: 5-3を題材に、`rqt_plot` の使い方（軸の範囲・保存）、`ros2 bag record/play`、再生してグラフを見直す。記録の終わらせ方（1）として、時間を指定する（`target_generator` に終了の時刻を持たせ、ノードが終わったらlaunch全体（bagの記録を含む）を止める。launchの `on_exit=Shutdown()`）。5-3と5-4の記録を同時に再生し、remapで分けて1つの `rqt_plot` に重ねる。
  - 6-2 条件で終わらせる: 記録の終わらせ方（2）として、見張りのノード `goal_monitor` が、走った距離がゴールの距離（450 m）に達したら（ゴールラインを通過したら）終わる。車両はゴールで止まらず、目標の階段どおりに走り続ける（2026-09-27、ユーザー判断）。6-1の `end_time` が時間切れの役を担い、早く起きたほうで終わる。案A（速度を積み上げて走った距離を出す。5-3・5-4の両方で使え、Gazeboが動かない環境でも学べる）から始め、同じノードのパラメータ `use_odometry` で、案B（5-4のGazeboのオドメトリの位置を使う。自分で積み上げないので、取りこぼしや時間の測り方による誤差が乗らない）に切り替える。強化学習への本命は案B（2026-09-26、ユーザー判断）。
  - 6-3 数にする: 解析のノードで、bagを再生しながら指標を計算し、条件（既定、`tau_brake` 1.0、5-4のGazeboの物理など）ごとの比較表を作る。Python版を学び、C++版はサンプルを動かす程度（ほかのノードがPythonのままでも、トピックでつながる。2026-09-26、ユーザー判断）。最後に、比較表の数がステップ6の報酬の候補になることを示す。指標の計算はROS2を使わない `metrics.py` に分け、5-2の閉ループの計算とも答え合わせする。時間は、記録の時刻（PCの時計が飛ぶ）ではなく「受け取った速度の数 × プラントの周期」で数え、再生は一時停止（`-p`）で始めて、解析のノードがつながってから進める（つながる前の分が届かず、最初の段がまるごと欠けたことがあったため。2026-09-27、Claude独自判断）。
- 指標（2026-09-26、ユーザー判断で6つとも採用）: 行き過ぎ量（%）、立ち上がり時間（目標変化の10%→90%）、整定時間（±2%）、定常偏差、追従誤差の二乗平均（RMS）、ペダルが±1に張り付いた時間。RMSは記録全体で1つ、ほかの5つは目標の段ごとに出す（ユーザーは成果物を見てから結論を出す。暫定）。本文で詳しく解説するのは行き過ぎ量・整定時間・RMSの3つで、残りはコードと表に含め、読み方を短く添える。
- 完了条件: 記録したbagから、条件ごとの指標の比較表を作り、制御の効き方（立ち上がり・行き過ぎ・定常偏差）の違いを説明できる。
- PlotJugglerは任意（導入する場合は、事前にユーザーの承認を得る）。

## 手順書の方針（決定）

- **分割単位**: フェーズごとに分け、着手直前に作る。フェーズ内でも、OSSツール別、Python用/C++用など必要に応じて分割する（実績はこの下の「手順書一覧」を参照）。
- **図の活用を推奨**: 通信の流れ・ノード構成・ビルドの流れなどは図にする。図表は mermaid を基本とするが、mermaid を表示できない環境があるため（ユーザー指摘）、**同じ内容のSVGを `docs/img/` に作成して併記する**（本文にはSVGを画像として表示し、mermaid版は `<details>` に残す）。SVGは生成スクリプトで作った手描き相当のもので、図を直すときはmermaidとSVGの両方を更新する。画面のスクリーンショット（PNG。フェーズ5-0の冒頭のGazeboの画面）は図ではないので、mermaid版は置かず、代替テキストと説明の文を添える（2026-09-28）。
- **内容**: 各手順書に、実行コマンドとサンプルコードを記載する。サンプルコードは、フェーズ3〜4では両言語の完全版を載せる（ユーザー判断。手順書は「各節冒頭の「主なAPI」表でAPIを把握 → サンプルと解説を読んで理解 → 値やフィールドを変えて改造する」の形にする（2026-09-23にユーザー指摘で、仕様だけから自分で書かせる形を改めた）。サンプルは隠さず常時表示とし、ファイルごとの解説を充実させる（2026-09-21にユーザー指示で`<details>`を廃止））。公式チュートリアルの丸ごと転載はしない（自分の言葉での再構成、必要最小限の抜粋には出典を明記）。
- **書き方の細則**: 実行手順の直後の「期待する結果」、サンプルコードの概要コメント、後の節への参照の書き方、個人の練習環境への指摘を手順書に書かないこと、は、プロジェクトの `CLAUDE.md` の「手順書（`docs/`）の書き方」節に従う（2026-09-24）。
- **参考資料**: 末尾に「公式ドキュメント」節を設け、公式ページ（Jazzy版に固定したURL）とQiita等の日本語記事のURLを載せる。URLは推測せず、実在を確認したものだけを記載する。
- **Python/C++の差分の記録**: 空欄の「記録用の表」（読者が自分で埋める前提の表）は置かない（2026-09-23、ユーザー判断。「学習資料は他の人が再利用しうるため、個人の進捗記録が唯一の目的の表は不適切」との指摘による）。Python・C++の両方を実装するフェーズでは、各手順書の該当節末尾に著者（Claude）が調べて書いた「Python版とC++版の違いのまとめ」を置き、読者はそれを読んで理解を確認する形にする。フェーズ1・フェーズ4のような言語比較でない振り返りも、同様に本文の解説として書き切り、空欄の表にしない。
