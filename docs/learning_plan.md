# 学習プラン（ROS2 × Python/C++ でシミュレーション環境を作る）

`docs/idea_origin.md` のロードマップ（ステップ0〜7）を、学習の5テーマ×2言語の視点で実行順に並べ直したもの。技術選定の決定事項（Jazzy、PI制御、1D質点、オイラー法、rqt_plot 等）はidea_origin.mdを正とし、ここでは繰り返さない。

## 目的とゴール

- 目的: ROS2の実務スキルを一通り身に着けながら、「慣性のある車両を目標速度に追従させるシミュレーション」を完成させる。
- 5テーマ: (A) `ros2` コマンド / (B) パッケージ作成 / (C) launchファイル / (D) ノードのプログラミング / (E) 有名OSSの活用。
- 各テーマを **Python（rclpy）とC++（rclcpp）の両方**で試す。ただし言語差が本質でない項目は片方で足りる（下表の「言語」列）。ノードのプログラミング（D）は、フェーズ3-1（トピック）だけ両言語を必須とし、3-2〜3-5のC++版は任意とする（2026-09-24、ユーザー判断。フェーズ5がPython中心のため）。

## フェーズ計画

各フェーズの完了条件を満たしてから次へ進む。所要は目安（1コマ＝1〜2時間の学習セッション）。

### 環境構築（ステップ0）— 半日

- 内容: WSL2・Ubuntu 24.04・ROS2 Jazzyの導入（`docs/setup_wsl2_ros2.md`）。別ドライブへの移動（2b節）と、GitHubの認証・Claude Codeの環境（7節）は任意。
- 完了条件: `ros2 run demo_nodes_cpp talker` と `ros2 run demo_nodes_py listener` の間でメッセージが届く。フェーズ0（読み物）とは、どちらを先にしてもよい。

### フェーズ0: ROS2の概要（読み物）— 1コマ

- 内容: ROS2のプロトコルの基礎（DDS・RMW・QoS・discovery）、ROS2で実現できること、基本用語、学習しなければならない概念の地図、よく使われる周辺開発ツールを整理した読み物。コマンド実行はしない。
- 完了条件: 本文の用語（ノード・トピック・サービス・アクション・パラメータ・DDS・RMW・QoS等）を自分の言葉で説明できる。

### フェーズ1: 触って観察する（A・E）— 1〜2コマ

- 内容（1-1）: turtlesimを動かし、`ros2 node/topic/service/param/action/interface`、`rqt_graph`、`rqt_console` で通信を観察する。
- 完了条件: turtlesimの `/turtle1/cmd_vel` の型（Twist）を `ros2 interface show` で説明でき、`ros2 topic pub` で亀を動かせる。

### フェーズ2: パッケージとビルド（B）— 1コマ

- 内容（1-0）: ワークスペースを作り、`ament_python` と `ament_cmake` の空パッケージを1つずつ作成、`colcon build` → `source install/setup.bash` → `ros2 run`。
- 完了条件: 両パッケージの `package.xml` / `setup.py`（`setup.cfg`）/ `CMakeLists.txt` の役割を自分の言葉で説明できる。
- 注意: `--symlink-install` の有無での挙動差（Pythonは再ビルド不要になる）を1回体験する。

### フェーズ3: ノードの基本（D）— 3〜4コマ

同一仕様をPython → C++の順に実装する（C++版が必須なのは3-1だけ。3-2〜3-5のC++版は任意）。各手順書の「Python版とC++版の違いのまとめ」節に差分を書き下し、1-7振り返りの材料にする（読者が空欄を埋める形式は廃止。2026-09-23、ユーザー判断）。

| 段階 | 題材（標準インターフェース） | 追加で体験すること |
|---|---|---|
| 1-2 | String talker/listener → Float64+timer → Twistでturtlesim操作 | QoSを変えて「つながる/つながらない」を確認（①と④の2通りで可。全7通りは任意）。Pythonのpub × C++のsubの相互接続 |
| 1-3 | パラメータ化（周期・内容） | `ros2 param set` と起動時YAML |
| 1-4 | AddTwoInts、Trigger | 同期/非同期呼び出しの違い、C++のfuture扱い。**概要を掴む程度でよい**（Pythonのサーバ＋CLIでの呼び出しまで。クライアント・Trigger・C++版は任意） |
| 1-5 | Fibonacci（フィードバック付き） | goal/feedback/resultの流れ、キャンセル。**概要を掴む程度でよい**（フェーズ5では使わないため。実装は任意の発展） |

- 完了条件: 上表を動かし（両言語が必須なのは1-2のtalker/listener等（3-1）だけ。1-4・1-5は概要の理解までで可）、各手順書の「Python版とC++版の違いのまとめ」節（コード量・型・ビルド手順・つまずき）の内容を自分の言葉で説明できる。

### フェーズ4: launchで束ねる（C）— 1〜2コマ

- 内容（1-6）: 1-2のpub/subを1つのlaunchで起動。引数（`DeclareLaunchArgument`）で Python版/C++版ノードを切り替え、混在起動も確認。パラメータYAMLの読み込み、`remap`、`namespace`、`LaunchConfiguration`。
- 完了条件: 引数1つで4通り（Py×Py, Py×C++, C++×Py, C++×C++）の組み合わせを起動できる。
- 振り返り（1-7）: フェーズ2・3-1〜3-5の各「Python版とC++版の違いのまとめ」節を読み返し、コード量・型の扱い・ビルド手順・つまずきの傾向を自分の言葉で整理する（フェーズ5の言語方針は下記のとおり既に決定済みのため、この振り返りは言語選定のためではなく、C++の勘所を再確認する目的で行う）。

### 間章: コンポーネント指向でノードを組み立て直す（B・C・D）— 1〜2コマ

- 内容: フェーズ3-1のC++版 `talker` / `listener` を、コンポーネント（`rclcpp_components`。`main` を持たず、共有ライブラリとしてビルドし、どのプロセスに入れるかを起動時に決めるノード）として新しいパッケージ `learn_components` に作り直す。コンテナへの手での読み込み（`ros2 component load`）、自動生成される単独の実行ファイル、launch（`ComposableNodeContainer`）の3通りで動かし、マイクロサービスの考え方との対応を整理する。
- 言語: C++のみ（コンポーネントの仕組みがC++専用のため。2026-09-24、ユーザー判断）。フェーズ5はPythonで書くので、この章の成果物には依存しない。
- 完了条件: コンポーネントとふつうのノードの違い（`main` が無い、`NodeOptions`、登録マクロ、共有ライブラリ）と、「ノードの中身」と「配置」を分ける利点を自分の言葉で説明できる。

### フェーズ5: 車両シミュレーション本体（D・C）— 4〜6コマ

- 5-1（ステップ2）疑似プラントノード: 1D質点＋アクセル/ブレーキ別の一次遅れ＋オイラー積分。入力は指令、出力は現在速度。モデル部はトピックI/Fから分離しておく。
- 5-2（ステップ3）PI制御ノード: Kp/Kiをparameter化し、YAMLで与えて `ros2 param set` で調整。ループが閉じて目標速度に追従する。
- 5-3 launch化: プラント・制御・目標速度発生ノードを1つのlaunchで起動。
- 完了条件: ステップ入力の目標速度に対して追従し、アクセル/ブレーキの非対称性の影響をグラフで説明できる。
- 言語方針（決定）: **Pythonをベースに実装する**。C++版は参考程度に、余力があれば作る（作る場合はトピックI/Fを同じにして、Python版と差し替え可能にする）。

### フェーズ6: 可視化・記録（E）— 1〜2コマ

- 内容（ステップ4）: `rqt_plot` で目標/実速度/制御出力を表示、`ros2 bag record/play` で記録・再生。再生データをPython/C++の購読ノードで解析（例: 追従誤差の二乗平均を算出）。余力があればPlotJuggler。
- 完了条件: 記録したbagから制御の効き方（立ち上がり・オーバーシュート・定常偏差）を評価できる。

### フェーズ7: OSSの拡張活用（E）— 任意・数コマ（ステップ7・5に対応）

- 範囲は固定せず、**実行時に段階的に広げる**（決定）。目安の順序は次のとおりで、各段階の着手時にQA表へ記録し、進めるか止めるかを判断する。idea_origin.mdのステップ番号順（Gazebo＝ステップ5が先）とは逆に、負荷の軽いものから順に並べている（意図的）。
  1. tf2（ステップ7。broadcaster/listener。Python中心、C++は任意）
  2. URDF/xacro＋RViz2で車両の簡単なモデル表示（ステップ7）
  3. ros2_controlの概念把握（ステップ7）
  4. Gazebo Harmonic（ステップ5。PCスペック次第で、負荷を見て判断）
- ステップ6（強化学習によるゲイン調整）は独立した発展課題として、フェーズ5完了後に別途計画する。

## 手順書の方針（決定）

- **分割単位**: フェーズごとに分け、着手直前に作る。フェーズ内でも、OSSツール別、Python用/C++用など必要に応じて分割する（実績はこの下の「手順書一覧」を参照）。
- **図の活用を推奨**: 通信の流れ・ノード構成・ビルドの流れなどは図にする。図表は mermaid を基本とするが、mermaid を表示できない環境があるため（ユーザー指摘）、**同じ内容のSVGを `docs/img/` に作成して併記する**（本文にはSVGを画像として表示し、mermaid版は `<details>` に残す）。SVGは生成スクリプトで作った手描き相当のもので、図を直すときはmermaidとSVGの両方を更新する。
- **内容**: 各手順書に、実行コマンドとサンプルコードを記載する。サンプルコードは、フェーズ3〜4では両言語の完全版を載せる（ユーザー判断。手順書は「各節冒頭の「主なAPI」表でAPIを把握 → サンプルと解説を読んで理解 → 値やフィールドを変えて改造する」の形にする（2026-09-23にユーザー指摘で、仕様だけから自分で書かせる形を改めた）。サンプルは隠さず常時表示とし、ファイルごとの解説を充実させる（2026-09-21にユーザー指示で`<details>`を廃止））。公式チュートリアルの丸ごと転載はしない（自分の言葉での再構成、必要最小限の抜粋には出典を明記）。
- **書き方の細則**: 実行手順の直後の「期待する結果」、サンプルコードの概要コメント、後の節への参照の書き方、個人の練習環境への指摘を手順書に書かないこと、は、プロジェクトの `CLAUDE.md` の「手順書（`docs/`）の書き方」節に従う（2026-09-24）。
- **参考資料**: 末尾に「公式ドキュメント」節を設け、公式ページ（Jazzy版に固定したURL）とQiita等の日本語記事のURLを載せる。URLは推測せず、実在を確認したものだけを記載する。
- **Python/C++の差分の記録**: 空欄の「記録用の表」（読者が自分で埋める前提の表）は置かない（2026-09-23、ユーザー判断。「学習資料は他の人が再利用しうるため、個人の進捗記録が唯一の目的の表は不適切」との指摘による）。Python・C++の両方を実装するフェーズでは、各手順書の該当節末尾に著者（Claude）が調べて書いた「Python版とC++版の違いのまとめ」を置き、読者はそれを読んで理解を確認する形にする。フェーズ1・フェーズ4のような言語比較でない振り返りも、同様に本文の解説として書き切り、空欄の表にしない。
